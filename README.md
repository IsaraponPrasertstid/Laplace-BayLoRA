# Personalising LLMs with Few Labels via Bayesian DPO

This repository implements **Bayesian DPO**, a method for personalising large language models (LLMs) using only a small number of human preference labels.

We adapt a Bayesian optimisation framework for interactive ranking from pairwise comparisons to **DPO-trained LLMs**, replacing Gaussian-process preference models with Bayesian LoRA uncertainty approximations. We evaluate three **Bayesian approximations** **(MC Dropout (MCD), Laplace, and SWAG)** and compare them against a non-Bayesian baseline. Empirically, MCD achieves the best performance in our experiments.

---


Reinforcement Learning from Human Feedback (RLHF) is effective but expensive

**This project investigates**:

> Can we personalise an LLM to an individual user from only a small number of pairwise preference labels?

Our approach combines:
	- Bayesian active selection of response pairs: we estimate uncertainty over candidate utilities and query the user on comparisons that are expected to be maximally informative (MCD by default; Laplace and SWAG as alternatives).
	- Efficient preference learning via DPO while training only LoRA parameters.

Across our experiments, MCD provides the strongest results relative to Laplace, SWAG, and a non-Bayesian selection baseline.

---

## Key Idea: Bayesian DPO

We adapt the Bayesian optimisation framework from:

- **Interactive Ranking from Pairwise Comparisons**  
  TACL 2020 (GPPL)  
  https://arxiv.org/pdf/1911.10183

to LLMs trained with **Direct Preference Optimisation (DPO)**.

### GPPL setting
- Latent utility function over items
- Modelled using a Gaussian process
- Active learning selects the most informative pairwise comparisons

### Our setting (Bayesian DPO)
- We replace the Gaussian process in GPPL with a Bayesian LoRA surrogate built on a DPO-trained LLM.
- We approximate the Bayesian posterior and uncertainty using MCD, Laplace, or SWAG.

## Data

We use a topic-based summarisation dataset (**DUC2004_summarisation_Documents**) from the DUC 2004 benchmark.

[https://duc.nist.gov/duc2004/
](https://duc.nist.gov/duc2004/)

The dataset contains:
- 50 topics, each consisting of a cluster of multiple related news articles.
- For each topic, a document set that is concatenated into a single input post.
- Four human-written reference summaries per topic, used for evaluation and anchor selection.

We concatenate all documents within each DUC 2004 topic into a single source text and generate a mixed candidate pool of summaries to reflect real-world variation in summary quality and style. Each candidate summary is constrained to around 100 words.

For each topic, we construct three types of candidates:
- Good extractive summaries: sentence-level extraction that preserves the original document order, producing coherent summaries without truncating sentences.
- Bad extractive summaries: extraction with shuffled sentence order and occasional rough truncation, which can cut mid-sentence to create lower-quality, less coherent summaries.
- Abstractive summaries: generated by a Llama instruction-tuned model, producing concise paraphrased summaries.

This mixed pool provides diverse candidate responses for preference-based learning and active selection, covering both well-formed and degraded summaries alongside model-generated abstractive ones.


The reference summaries are not used for training the preference model, but are used for: **Anchor-based evaluation**

The DUC 2004 dataset does **not** provide preference labels. In principle, we could recover a full ranking over candidate summaries by asking an LLM judge to compare every pair, but this quickly becomes computationally infeasible: a full pairwise tournament over \(N\) candidates costs \(\mathcal{O}(N^2)\) judge comparisons (approximately \(N(N-1)/2\)).

To make evaluation posible, we use an **anchor-based evaluation** protocol:

- We select a small set of **anchors** (we use \(M=32\)).
- For each candidate summary, we estimate a relevance/quality score as its **win-rate against the anchors**.
- This reduces evaluation cost from \(\mathcal{O}(N^2)\) to \(\mathcal{O}(NM)\).  
  For example, with \(N=1000\) candidates and \(M=32\) anchors:
  - Full tournament: \(\approx 1000 \cdot 999 / 2 \approx 5\times 10^5\) comparisons
  - Anchor-based: \(1000 \cdot 32 = 3.2\times 10^4\) comparisons (over an order of magnitude cheaper)

This approach avoids judging all candidate pairs while still producing a meaningful relative ranking signal.

### How we choose anchors (why references help)

Anchor selection matters. If anchors are sampled uniformly at random, they may over-represent only the extreme tails (very strong or very weak summaries), which can make comparisons less informative and rankings less stable.

To ensure anchors are representative, we select anchors to **cover the candidate-quality distribution**:

- When reference summaries are available, we compute a rough quality proxy for each candidate using **ROUGE-L** against the four human references.
- We then select anchors **stratified across the ROUGE-L score distribution** (e.g., bottom / middle / top regions). This ensures coverage of low-quality, medium-quality, and high-quality candidates.

Importantly, **reference summaries are never used as supervision for preference training**. They are only used to pick anchors that cover the distribution

## Simulated User (LLM Judge)

Our method requires pairwise preference labels (A/B comparisons). Since the dataset (DUC 2004) does not include such labels, we use a **simulated user** in the form of an **LLM judge** to generate preference comparisons reproducibly.

Recent work suggests that LLM-based evaluators can act as strong oracles for preference-style judgements:

- **LLM evaluators can outperform traditional automatic metrics** for many tasks (e.g., Chen et al., 2023).
- For summarisation in particular, *LLM-as-a-judge* style evaluations have been shown to correlate strongly with humans. In the DPO setting, (Rafailov et al., 2023) report that GPT-4 judgements when appropriately prompted-align well with human preferences.
- Reported GPT-4 vs human agreement is often comparable to (or higher than) **inter-annotator agreement** on the same summarisation comparisons (Muldrew, 2024).

### Judge model

We generate pairwise preference labels using:

- **Judge**: `meta-llama/Llama-3.2-3B-Instruct`  ([https://huggingface.co/meta-llama/Llama-3.2-3B-Instruct](https://huggingface.co/meta-llama/Llama-3.2-3B-Instruct))


### Prompting protocol
  
We adapt the judge prompt format from: Muldrew et al. (2024):  [https://arxiv.org/pdf/2402.08114](https://arxiv.org/pdf/2402.08114)

The judge is prompted to compare **Summary A vs Summary B** for the same source post and output a structured decision in the form:

- `Preferred: A` or `Preferred: B`
- plus a short one-sentence justification

## Our Method: Bayesian DPO with LoRA

We replace the GP preference model (as used in GPPL-style methods) with a **DPO-trained, LoRA-adapted LLM** that acts as the utility surrogate:

- **Base model:** a Qwen/Qwen2.5-0.5B causal LLM ([https://huggingface.co/Qwen/Qwen2.5-0.5B](https://huggingface.co/Qwen/Qwen2.5-0.5B))
- **Adaptation:** LoRA (trainable adapters; base weights frozen)
- **Preference objective:** Direct Preference Optimisation (DPO)

#### Bayesian modelling of the surrogate

We support multiple Bayesian approximations over the LoRA-adapted policy. In our experiments, **MCD** is the best-performing option, with **Laplace** and **SWAG**

**MC Dropout (the best)**
1. Train a MAP LoRA policy using DPO
2. Enable dropout at inference time and draw multiple stochastic forward passes
3. Estimate a posterior over candidate utilities from Monte Carlo samples
4. Select the next comparison using Bayesian acquisition functions (e.g., uncertainty-based querying)

**Laplace**
1. Train a MAP LoRA policy using DPO
2. Estimate curvature over LoRA parameters using **K-FAC**
3. Construct a **Laplace posterior** over LoRA parameters (diagonal or diagonal + low-rank, depending on configuration)
4. Propagate parameter uncertainty to candidate utility predictions via linearization
5. Select queries using Bayesian acquisition functions (e.g., EI / uncertainty-aware sampling)

**SWAG**
1. Train the LoRA policy using DPO while periodically collecting LoRA snapshots
2. Fit a SWAG posterior (mean + diagonal variance + low-rank subspace)
3. Sample LoRA parameters to obtain a posterior over candidate utilities
4. Select queries using Bayesian acquisition functions

--- 

#### Propagating uncertainty into utility space (MCD vs. Laplace/KFAC vs. SWAG)

In GPPL, the Bayesian model is defined **directly over latent utilities**, so the posterior is already aligned with the active-learning objective (ranking items by utility).

In Bayesian DPO, the Bayesian object depends on the approximation we use (dropout masks, curvature, or snapshots).
Regardless of the approximation, **active learning needs uncertainty over pairwise utility differences**
\[
\Delta u(x; y_i, y_j) \;=\; u(x,y_i) - u(x,y_j),
\]
because acquisition functions choose the next query based on how uncertain we are about which candidate is better.

Below we describe how each Bayesian approximation yields a posterior over utilities.

---

##### Utility definition (DPO)

We use the standard DPO-style implicit utility (log-likelihood ratio vs. a frozen reference), computed over response tokens:
\[
u_\theta(x,y) \;=\; \beta \Big(\log p_\theta(y\mid x) - \log p_{\text{ref}}(y\mid x)\Big).
\]

We score a pool of candidates \(y_1,\dots,y_N\) for a fixed input \(x\), producing a **utility vector**
\[
u \;=\; [u(x,y_1),\dots,u(x,y_N)]^\top.
\]

Active learning then relies on (an approximation to) a **utility posterior**, commonly summarized by
\((\mu,\Sigma_u)\), where \(\mu \approx \mathbb{E}[u]\) and \(\Sigma_u \approx \mathrm{Cov}(u)\).

---

##### MC Dropout (MCD): posterior in utility space via stochastic forward passes

MCD does **not** construct an explicit Gaussian posterior over parameters. Instead, it induces an implicit posterior by
enabling dropout at inference time and sampling multiple stochastic forward passes.

1. **Sample utilities** (dropout ON): for \(t=1,\dots,T\),
   \[
   u^{(t)}(x,y) \;=\; u_{\theta,m_t}(x,y),
   \]
   where \(m_t\) is a sampled dropout mask.

2. **Estimate utility mean and covariance** from the samples:
   \[
   \mu \;=\; \frac{1}{T}\sum_{t=1}^T u^{(t)}, 
   \qquad
   \Sigma_u \;\approx\; \mathrm{Cov}\big(\{u^{(t)}\}_{t=1}^T\big).
   \]

3. **Pairwise uncertainty** can be derived either from samples directly (by sampling \(\Delta u^{(t)}\)) or from
   \((\mu,\Sigma_u)\) via:
   \[
   \mathrm{Var}(\Delta u_{ij}) \;=\; \Sigma_{u,ii} + \Sigma_{u,jj} - 2\Sigma_{u,ij}.
   \]

**MCD gives uncertainty in *utility space* "for free" because we sample utilities directly.**

---

##### Laplace / KFAC: parameter posterior => utility posterior via linearization/probing

Laplace/KFAC constructs an explicit approximate posterior over LoRA parameters:
\[
\theta \sim \mathcal{N}(\theta_{\text{MAP}}, \Sigma_\theta).
\]

To align this with ranking, we propagate parameter uncertainty into utility space via a local linearization:
\[
u_\theta \approx u_{\theta_{\text{MAP}}} + J(\theta-\theta_{\text{MAP}}),
\quad\Rightarrow\quad
\Sigma_u \approx J\Sigma_\theta J^\top,
\]
where \(J = \partial u/\partial\theta\).

Since computing the full Jacobian \(J\) is infeasible for LLMs, we estimate utility uncertainty using
**directional finite differences**:

1. **Mean utilities (MAP):** \(\mu = u_{\theta_{\text{MAP}}}(x,\cdot)\)

2. **Probe high-variance directions:** for selected parameter directions \(d_k\) (e.g., low-rank directions from KFAC),
   \[
   z_k \;\approx\; \frac{u(\theta+\epsilon d_k)-u(\theta-\epsilon d_k)}{2\epsilon}.
   \]

3. **Accumulate covariance in utility space:**
   \[
   \Sigma_u \;\approx\; \sum_k \mathrm{Var}(d_k)\, z_k z_k^\top \;+\; \frac{1}{M}\sum_{m=1}^M z_m z_m^\top,
   \]
   where the second term can be used to approximate remaining diagonal/residual uncertainty.

**Laplace starts in parameter space, so we must explicitly propagate uncertainty into utilities.**

---

##### SWAG: parameter posterior from snapshots => utility posterior via sampling

SWAG (Stochastic Weight Averaging–Gaussian) approximates a posterior over parameters using **training trajectory snapshots**
instead of curvature.

1. **Collect LoRA snapshots:** after burn-in, periodically store LoRA parameters
   \(\{\theta^{(s)}\}_{s=1}^S\) during continued DPO training.

2. **Fit a SWAG Gaussian approximation:** SWAG maintains running estimates of:
   - mean: \(\bar\theta\)
   - diagonal variance: \(\sigma^2_{\text{diag}}\)
   - low-rank subspace (from recent centered snapshots)

   yielding an approximate posterior:
   \[
   \theta \sim \mathcal{N}(\bar\theta, \Sigma_\theta^{\text{SWAG}})
   \quad\text{(diag + low-rank)}.
   \]

3. **Sample parameters and score utilities:** draw \(T\) parameter samples \(\theta^{(t)}\sim q_{\text{SWAG}}(\theta)\),
   then compute:
   \[
   u^{(t)} = u_{\theta^{(t)}}(x,\cdot).
   \]

4. **Estimate \((\mu,\Sigma_u)\) in utility space** from sampled utilities exactly as in MCD:
   \[
   \mu = \frac{1}{T}\sum_{t=1}^T u^{(t)}, 
   \qquad
   \Sigma_u \approx \mathrm{Cov}(\{u^{(t)}\}_{t=1}^T).
   \]


**SWAG is "Bayesian in parameter space" like Laplace, but propagates to utilities by *sampling* rather than
finite-difference probing.**

---

##### Using \((\mu,\Sigma_u)\) for query selection

Once we have \((\mu,\Sigma_u)\), we can compute uncertainty over each pairwise gap \(\Delta u_{ij}\) and apply Bayesian
acquisition functions (e.g., uncertainty sampling, information gain proxies, EI-style criteria) to choose the next
pair \((i,j)\) for the user/judge to compare.

# Acquisition function 
Similar to Simpson et al. 2020 ([https://arxiv.org/pdf/1911.10183](https://arxiv.org/pdf/1911.10183))


#### Active learning loop (common to all Bayesian modes)

At each round, we:
1. Score candidates for the current topic using the current policy
2. Use the chosen Bayesian approximation to estimate uncertainty over utilities
3. Select an informative pair of candidates via an acquisition function
4. Obtain a preference label (simulated user aka LLM-judge)
5. Update the LoRA policy with DPO on the accumulated preference pairs
